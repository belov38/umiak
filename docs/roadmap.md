# Roadmap: области для brainstorm

Каждая область — отдельный тред T3 Code (независимые области идут параллельно, каждая в своём git worktree и ветке): brainstorm → спецификация в `docs/specs/` → согласование с пользователем. После согласования спецификации brainstorm-тред закрывается (settle), реализация идёт в отдельном треде и ветке `sN-impl` (план в `docs/plans/`), master сливает ветки в main. Архитектура: `docs/architecture.md`.

Ограничения PoC на `pve`: VMID от 500, не больше 8 GB RAM на всё, хранилище `local-lvm`. Разрешено создать пользователя, токен, pool и SDN Simple zone + VNet. Существующие VM, LXC и `vmbr0` не трогать.

Решение Ильи 2026-10-29: время создания sandbox не оптимизируем, до ~1 min допустимо. Warm pool в MVP не входит: Linux создаётся холодным клоном (~12 s), `failFast` / `pool_exhausted` (S6, S7) не реализуются, пул остаётся задачей фазы 2. Windows (S9) и `linux-desktop` (S10) тоже без спящих пулов. Для Windows до 5 min допустимо, 2–3 min — хорошо: create идёт холодным путём S9 (клон шаблона + sysprep specialize при первой загрузке), спайк vTPM + `suspend --todisk` не нужен.

Приёмка реализации: master не сливает ветку `sN-impl` только по отчёту исполнителя. Независимый тестовый субагент собирает, прогоняет линтеры и тесты и проверяет поведение на `pve`; найденное исправляет отдельный тред, после чего проверка повторяется.

Dev-стенд control plane (решение 2026-10-30): unprivileged LXC CT 590 на `pve` (`vmbr0`, 3 GB сверх лимита sandbox; 2026-10-31 Илья разрешил 6 GB — образ web (Next) не собирался в 3 GB), в нём docker compose; адрес CT в IPSet `umiak-gateway`. В проде control plane один на платформу (Kubernetes), а на нодах Proxmox в `umiak-gateway` — адрес балансировщика gateway. Имена dev-стенда (2026-10-30): агенты — `tunnel.192-168-68-90.sslip.io` (LAN, dev CA, который пинит агент), превью — `*.umiak.100-64-10-7.sslip.io` (tailnet, dev CA), с S15 (2026-11-02) dashboard/API/MCP — LAN HTTP на CT590 (:4180/app, :8080, :4180/mcp), Keycloak/oauth2-proxy остановлены, Serve mappings удалены; OIDC-откат одним deploy с `UMIAK_DEVCP_AUTH_MODE=oidc`; всё в `infra/dev-cp/` (README «Names and TLS»).

Миграции БД (`db/migrations/NNNN_*.sql`, решение master 2026-10-31): номера зарезервированы по областям, чтобы параллельные треки не сталкивались. `0100–0199` — S2 (`tunnel`); `0200–0299` — runtime: S6 и изменения таблиц runtime из S7 (`0204`, `0205`) и S8 (`0206_sandbox_block_meta.sql`); `0300–0399` — S7; `0400–0499` — S8 (`0400_environments_runtime.sql`: environments команд переезжают из `identity` в `runtime`); по решению master S10 (таблицы рабочего стола рядом с identity/web) занял внутри этого блока `0401–0405` (`0401_desktop`, `0402_desktop_disconnect`, `0403_desktop_policy_revocation`, `0404_desktop_drop_block`, `0405_desktop_turn_attempt`); применённые номера не перенумеровываются, следующий свободный номер блока — `0406`. Исключение по решению master: колонки `reason` и `output_truncated` таблицы S6 `runtime.commands` из приёмочных правок S7 лежат в `0304_command_output.sql` (диапазон S7), с комментарием в миграции. Новые области берут свой диапазон здесь, прежде чем добавлять миграции.

Сквозной тест на dev-стенде (2026-10-31, в main): весь стек MVP на CT 590, сценарий `infra/dev-cp/e2e.sh` с Mac (login, create, exec, PTY, cp, превью token/sso, ssh, fork, snapshot, stop/resume, idle-stop, delete, оба SDK) — 20/20 PASS, независимая приёмка повторила прогон. Вход для Ильи — `infra/dev-cp/QUICKSTART.md`. Найденное в E2E закрыто веткой `fix-resume-sshca` (в main): worker при каждом resume/recover/reprovision заново отправляет агенту ключи SSH user CA, `umiak logs -f` выходит с кодом команды, `snapshot save --wait --json` пишет события `accepted`/`ready`/`error`; `create --from <snapshot>` переносит только диск, без env и секретов (S7 §8.3).

Доработки после приёмки S11 (2026-10-31, не блокируют MVP): API (S7) отдаёт сообщения агента без очистки (MCP их чистит сам); `exec_list` после kill ещё ~10 s показывает `running`; в S12 поду `mcp` нужен `preStop` sleep (по SIGTERM основной порт сразу закрывается).

Слоты шаблонов (решение master 2026-10-31): `linux` — 597/599, `windows` — 598, `linux-desktop` (S10) — 595/596 из диапазона dev-инфраструктуры 590–596 (CT 590 остаётся). S10 запущен параллельно с S9: сначала Linux, Windows desktop и вкладка Desktop в web — после слияния S9 и S8.

Доработки после приёмки S9 (2026-10-31): закрыты в `s9-followups` (в main). Snapshot работающей Windows теперь crash-consistent: пауза vCPU ~0,5–0,9 s без QGA/VSS, `consistency: "crash"` (зависание thaw в qemu-ga/VSS обойдено, первопричина не найдена — S9 §24.7); `secret_files_on_disk` → `snapshot_requires_stop`, повтор `UpdateSecrets`, повторы при lock qmeventd; шаблон `windows` и размер `4gb` в Payload (миграции `0207` и Payload `20261101_000000_windows_template`); мелочи агента и тест CLI исправлены. При слиянии S10 поправить порядок Payload-миграций (`20261031_105048_desktop_defaults` из `s10-impl`) и последний JSON-снимок.

Windows fork и saved snapshot (решение Ильи 2026-11-01, ветка `win-force-stop` в main): только из штатно остановленной VM. Работающая Windows без флага — `409 snapshot_requires_stop` с подсказкой `forceStop: true` / `--force-stop`; с флагом — graceful stop (Windows до 300 s) → снапшот `powered_off` → старт источника → fork. Тайм-аут shutdown — `shutdown_timeout` без снапшота; после готового снапшота fork не откатывается. `machines.clean_stop` (миграция `0208`): Windows без штатного выключения — `snapshot_requires_clean_stop`, Linux — `consistency: crash`. Доработки (не блокируют): отказ для остановленной Windows без `clean_stop` приходит асинхронно (fork `202` → `fork_failed`), стоит проверять в API; после `snapshotTaken` нет верхней границы повторов финальной транзакции; verify шаблона Windows при пересборке 598 может упасть на зависшем VSS thaw (`ThawFailedError` не ведёт в crash fallback) — проверить при пересборке; CLI `--wait` по умолчанию 5 min меньше худшего stop Windows (7 min).

Доработки после приёмки S10 (2026-11-01): W1-B — на Windows websocket-просмотрщик иногда чёрный (2 из 5 прогонов, Sunshine шлёт IDR раз в секунду; диагностика `web-server.log` снимается слишком поздно); окно в 3–6 s после разблокировки, когда билет с эпохой блокировки ещё обменивается (`unblockSandbox` без NOTIFY, обмен не проверяет `policy_revoked`); под нагрузкой отложенная перезагрузка Windows для смены имени срабатывает после claim (`winboot.go`); watchdog TURN не проверяет адрес на `lo`; посылка relay на запрещённый порт убивает свою аллокацию (задокументировать); TURN-TLS на 443 и выделенный адрес — S12 (фаза 2).
